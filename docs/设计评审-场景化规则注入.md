# 设计评审：按场景匹配规则，以及「放错位置」的代价

> 评审对象：本仓库当前版本（`26.10.5-1`）。
> 评审方式：读源码 + 在本机实测（cost-meter 真实账本 + `lib/rules.js` 实跑复现 + 逐行核对 DSH 宿主源码）。
> 结论先行：**「按场景自动匹配规则」值得做。但它省不了多少钱——规则本身只占会话成本不到 5%；它真正的收益是「容量」与「依从率」。而且有一个硬约束：动态内容只能落在消息尾部，绝不许进系统提示。**

## 1. 当前设计复核

### 1.1 分层与职责（清晰，无需大改）

```
lib/rules.js   纯逻辑：规范化 / 匹配 / 解析 / 渲染 / 往返     494 行，零依赖，可被 node --test 直跑
lib/index.js   宿主半体：存储 / 注入 / 面板接口 / 工具        725 行，仅用 node 内置模块
lib/client.js  面板半体：右侧栏 3+N 页签 UI                  2268 行
test/          1686 行测试（含源码级守卫）
```

「纯逻辑层 + 宿主半体 + 客户端半体」的三分是好的：注入语义能脱离 DSH 单测。**本次优化全部落在既有分层内。**

### 1.2 注入路径（含一处需要知道的耦合）

```js
ctx.systemPrompt.variable('ian_rules_body', (assembly) => rulesTextFor(cwdOfAssembly(assembly)))
ctx.systemPrompt.section({ name:'plugin:ian-rules', order:100, text:'{{ian_rules_body}}' })
```

- 走 `variable` 绕开 `{{}}` 严格插值，是**必需且正确**的：用户规则里的 `{{…}}` 永远不会打挂组装（宿主文档明确「substituted values are not scanned again」）。
- `variable` 回调**每个模型步都被调用一次**（`preStep` → `assemble` → `renderPrompt`，`step()` 内不重渲染）。目前文本只随 cwd 变，所以稳定。
- ⚠️ **耦合风险**：回调参数在插件里叫 `assembly`，但宿主公开类型是 `AssembleContext = {scope?, signal?}`（`dsh-system-prompt/lib/types/index.d.ts:37-45`）；`agent` 字段是 `dsh-agent/lib/index.js:291-297` 的 `assembleContextFor()` 额外塞进去的，**不在声明里**。插件依赖的 `assembly.agent.session.header.cwd` 因此是「实现细节级」的契约。建议：加一层防御 + 注释标明来源，并把变量名从 `assembly` 改成 `context`（现在这个名字会误导后来者以为能拿到整份 assembly）。

### 1.3 匹配与渲染

- `matchProject` 在所有启用项目里取**路径最长的一个**，只取一个（问题见 §3.2）。
- `append` = 全局 + 项目；`override` = 仅项目，且会明确告知被挡掉的全局条数（这点做得好）。
- 渲染两级标题（`##` 全局/项目，`###` 用户分组），编号连续，`MAX_SECTION_CHARS = 12000` 处按行截断。

### 1.4 数据模型

```js
rule    = { id, title, content, group, enabled }
project = { id, path, label, enabled, mode: 'append'|'override', rules[] }
doc     = { version: 1, enabled, global[], projects[] }
```

**没有任何「何时该用这条规则」的字段**——这正是场景匹配要补的东西（§4）。

## 2. 成本现实

### 2.1 实测价目与缓存命中率

本机 `cost-meter` 账本（`deepseek-v4.1-flash`，¥/百万 token）：

| 项目 | 价格 | 倍率 |
| --- | --- | --- |
| 缓存命中输入 | 0.003 | 1× |
| 缓存未命中输入 | 0.150 | **50×** |
| 输出 | 0.600 | 200× |

| 日期 | 调用 | 未命中 | 命中 | 命中率 | 实付 | 若全 miss |
| --- | --- | --- | --- | --- | --- | --- |
| 2026-10-05 | 367 | 1.46 M | 87.84 M | **98.4%** | ¥0.7288 | ¥13.64 |

**一天省下 ¥12.9。** 这是本项目最大的成本杠杆——比任何提示词微调大一到两个数量级。

### 2.2 关键分叉：改了系统提示，到底废掉多少前缀？

这不是「是/否」，取决于**路由能力**（`dsh-agent-loop/lib/index.js:1053`）：

```js
// dsh-agent-loop/lib/index.js:1052-1057（原文）
const commits = this.systemPrompt.project(renderedPrompt, {
  inHistory: preparedCall?.systemPromptUpdate === "in-history",
  startsSeries: startsRequestSeries
    || this.requestSurfaceGeneration !== this.session.surface.contentGeneration   // 压缩后
    || preparedCall?.toolUpdate === void 0 && this.toolsChanged(assembly.tools)  // 工具集变了
})
```

`project()`（同文件 `:264-282`）只有两条路：

- **`inHistory === true`** → 内容变了就在**尾部追加一条新的 system 消息**（`surfaceOp:"append"`），message 0 不动 → **前缀缓存保住**；代价是新增那段按未命中价付一次，且**历史永久变长**。
- **否则 / `startsSeries`** → 替换 message 0 并清空其它 system 节点 → **系统提示之后的全部内容一起失效**（工具定义 + 整个对话历史）。

谁支持 `in-history`？全仓**只有第一方 `dsh-llm-deepseek` 声明**（`dsh-llm-deepseek/lib/index.js:47`、`:306`）。本机经 `cordis.patch.yml` 用的是第三方 `@jiesou/dsh-commandcode-go-provider`，其 `lib/` 里**没有任何 `systemPromptUpdate` 声明** → `inHistory` 为假 → **走最坏分支**。
另外，压缩（`surface.contentGeneration` 变化）与「路由不支持工具更新且工具集变了」都会强制 `startsSeries`，即使有 `in-history` 也会切回替换分支。

### 2.3 四种策略的账单

基准：100 轮、平均上下文 5 万 token、规则集 7k token（约 50 条中等长度中文规则）。

| 策略 | 规则放哪 | 规则开销 | 相对现状 |
| --- | --- | --- | --- |
| **A 现状** | 系统提示，稳定不变 | **¥0.0021** | 1× |
| **B1 每步改系统提示**（本机路由：替换 message 0） | 系统提示 | **¥0.8550** | **407×** |
| **B2 每步改系统提示**（有 `in-history` 的路由：追加） | 系统提示 | ¥0.2089 | 100× |
| **C 每步改·走 `context()` 快照** | 消息尾部 | ¥0.1050 | 50× |

B2 的两笔账：追加的 100 × 7k token 按未命中价 = ¥0.105；膨胀出来的历史按命中价 = ¥0.104。而且终局上下文会涨到 **75 万 token**——远超窗口，必然触发压缩，压缩又强制 `startsSeries` → 兜回来还是一次全量失效。

**结论：无论哪种路由，把逐轮变化的内容放进系统提示都是错的；本机路由下错得最厉害。**

### 2.4 三个推论

**推论一：别拿「省 token」当改造理由。**
同一会话里，规则 ¥0.0021 vs 上下文历史 ¥0.015 vs 输出 ¥0.03。**规则占比不到 5%。**

**推论二：真正的收益是「容量」和「注意力」。**
- **容量**：`MAX_SECTION_CHARS = 12000` 是硬上限，而超限时**先丢项目专属规则**（§2.5 实测）。
- **注意力**：agent 面对 12000 字符规则墙 vs 8 条精准规则，依从率不是一个量级。
- **无缓存的供应商**：那种情况下 5 万 token × 100 轮 = ¥0.75，其中规则 ¥0.105，占 **14%**。场景匹配在那时是真省钱。

**推论三：现在的「保存并生效」代价随路由而异，且没人告诉用户。**
- 本机路由（替换 message 0）：长会话改一次规则 = 整个前缀重算。账本里昨天真实存在 29.5 万 token 的会话 → **一次 ¥0.0434**，是该会话规则静态预算的 21 倍；每个在跑的会话各付一次。
- 有 `in-history` 的路由：只是尾部追加一条 system 消息，便宜，但历史变长，最终靠压缩还债（压缩本身又是一次全量失效）。

> 建议（零成本降本）：面板保存后的文案加一句路由感知的提示，并提供「下个会话生效」。另外把这条判定做成**可自测**的：改一条规则后看下一个请求的 `cacheRead` 是否塌到接近 0——塌了就是替换分支。

### 2.5 实测复现：截断丢的是项目规则

```js
// 120 条全局规则 + 1 条项目专属规则
const full = renderRules(doc, '/tmp/proj', { limit: Infinity })   // 13962 字符
const cut  = renderRules(doc, '/tmp/proj')                        // 11968 字符（上限 12000）
full.includes('项目专属规则')  // true
cut.includes('项目专属规则')   // false  ← 项目规则被整条丢弃
```

截断按尾部切，渲染顺序是「全局在前、项目在后」，于是**最具体、最相关的那部分被牺牲掉**，而提示只说「已截断」，agent 不知道丢了哪几条。

## 3. 其它可优化项（按性价比排序）

### 3.1 截断优先级反转 —— 高性价比

改法（`lib/rules.js` 的 `truncateSection` / `renderRules`）：

1. **按具体性排序后再截断**：项目规则优先于全局规则。
2. **分层预算**：全局与项目各自配额，避免一方吃光。
3. **把被丢掉的规则标题列进提示**：让 agent 知道「本项目另有 N 条规则本轮未注入，可用 `ian_rules` 查询」——把静默失效变成可发现。
4. **不在规则中间切**：现在按最后一个换行切，可能落下「`104. **标题**`」却没有正文。

### 3.2 父级项目规则被静默丢弃 —— 高性价比

```js
const doc = { projects: [
  { path: '/repo',            rules: [根级约定] },
  { path: '/repo/packages/a', rules: [子包约定] } ]}
effectiveRules(doc, '/repo/packages/a').rules            // → ['子包约定']
renderRules(doc, '/repo/packages/a').includes('根级约定') // → false
```

monorepo 下这是高频场景：根目录写通用约定、子包写专属约定，结果子包会话**完全看不到根目录约定**；又因为不是 `override`，连「被挡掉的规则」那句提示都没有。

改法（建议 A）：
- **A. 祖先链合并**：cwd 的所有祖先项目按「根 → 叶」叠加，叶优先；`override` 仍只在自身层截断全局。
- **B. 至少告知**：注入文本里写「另有父级规则集 N 个未生效」。

### 3.3 位置纪律（**本次评审最重要的一条**）

| API | 落到模型输入哪里 | 能否放逐轮变化的内容 |
| --- | --- | --- |
| `systemPrompt.section()` | 系统提示 / 会话中段 system 消息 | ❌ 变了就要看路由脸色（本机 407×） |
| `systemPrompt.variable()` | 只是 section 内的取值 | ❌ 同上 |
| `systemPrompt.tools()` | 工具 schema（也在请求前缀里） | ❌ 同上 |
| `systemPrompt.context()` | **持久 user 快照，贴在消息尾部，且会被 supersede 而非累积** | ✅ 推荐 |
| `agent/pre-step` 注入 user 消息 | 消息尾部（DSH 自己的 skill 插件走这条） | ✅ 推荐，且有现成范式 |

补充事实：
- 宿主**不提供**缓存断点 / `cache_control` / partial section，插件无法标记「这段是稳定的」；唯一能做的就是保持前缀逐字节不变。
- `context()` 的快照会被 supersede（旧快照从模型可见表面移除），所以逐轮变化**不会**让历史堆满副本——证据：`dsh-agent-loop/lib/index.js:334-349` 的替换追踪 + 快照自带的「supersedes earlier runtime-context snapshots」声明行（`dsh-system-prompt/lib/index.js:135`）。
- `assemble()` 在 `agent/pre-step` **之前**发生（`preStep()` 里 `:907` 组装、`:911` 才派发 pre-step）。所以：**要按「当前这条用户消息」做匹配，`agent/pre-step` 是唯一拿得到 `messages` 的地方**——`context()` provider 只能拿到 `{agent, scope, signal}`。

### 3.4 `ian_rules list` 把全文无上限塞进工具结果 —— 中

`lib/index.js:662` 在 `list` 里用 `renderRules(..., { limit: Infinity })`，输出进 tool result 并**永久留在历史里**。规则多时一次调用吃掉上万 token。改法：默认摘要 + 命中统计，全文改为显式索取或新增 `lookup`。

### 3.5 其余清单

| 问题 | 位置 | 影响 | 改法 | 成本 |
| --- | --- | --- | --- | --- |
| 无全局总条数上限（300 × 200） | `rules.js:26` | 文档可达 6 万条 | 加总量上限或告警 | 低 |
| 接口无鉴权，同机任意进程可写规则并直达提示 | `index.js:572` | 本地提示注入面（README 已声明） | 拒绝非本机来源 + 正文按「数据非指令」框定 | 中 |
| `rulesTextFor` 里 `effectiveRules` 被算 2~3 次 | `index.js:303` | 无竞态（中间无 await），只是重复计算 | 快照一次再渲染 | 极低 |
| 依赖未声明的 `assembly.agent` 字段 | `index.js:279` | 宿主改内部结构即静默失效 | 防御 + 注释 + 变量改名 | 低 |

| 面板有「最占预算的 5 条」但无场景命中模拟 | `client.js:1191` | 场景匹配上线后无法验证漏命中 | 见 §4.5 | 中 |

## 4. 场景化规则注入：详细设计

### 4.1 目标与反目标

**目标**：每轮只把「和当前这件事相关」的规则全文送进上下文；常驻的底线规则照旧稳定注入。

**反目标**：不为了省 token 而让规则**静默消失**。宁可多注入，不可让用户以为规则生效了而其实没有。因此必须有：安全兜底开关、命中可见、漏命中可发现。

### 4.2 数据模型 v2（向后兼容）

```js
rule = { ...v1, mode: 'always' | 'auto', tags: string[] }   // mode 缺省 always，tags ≤ 8 个
doc  = { version: 2, ..., sceneMatching: 'off' | 'auto' }   // 缺省 off
```

兼容策略（**零回归**是硬要求）：

- v1 文档读进来：所有规则补 `mode:'always'`，文档补 `sceneMatching:'off'`。
- **行为不变式**：`sceneMatching:'off'` 或全部规则都是 `always` 时，渲染输出必须与旧版**逐字节相同** —— 用一条黄金测试守住。
- 新版面板**默认创建 `always` 规则**，用户主动开「按场景」才产生 `auto` 规则，避免升级后新规则悄悄不生效。
- `sanitizeDoc` 对未知字段本来就丢弃并补默认值，所以 v1 文件不会被写坏。

### 4.3 匹配算法（零依赖，约 120 行）

插件全程零依赖是它的气质，必须保持。

**信号**：① 当前用户消息原文（权重 3）② 最近 3 条消息（权重 1，衰减）③ 本会话出现过的文件路径 / 工具名（权重 2）④ cwd（沿用既有项目匹配，作**前置过滤**而非打分项）。

**分词**：ASCII 转小写按非字母数字切词；CJK 用**单字 + 二元字组**（「提交前跑测试」→ `提交/交前/前跑/跑测/测试`），不引分词器也能拿到接近词粒度的匹配。

**打分**：

```
score = Σ_hit(tag×3, title×2, content×1) × 1/(1 + log(1 + 正文长度/200))
```

长度归一化必需：否则一条 4000 字的巨型规则靠「什么都沾一点」通吃所有场次。

**选择**：超过阈值按分数降序，取到预算（建议每轮 2000 字符 / 约 1500 token）用尽；`always` 规则不参与竞争。

**抖动抑制（关键）**：同一会话内已注入过的规则集合**只增不减**（sticky）。理由：每步换一批会让 model 看到互相矛盾的规则快照，行为飘忽。

### 4.4 注入位置（三层）

| 层 | 放什么 | 走哪条 API | 变化频率 |
| --- | --- | --- | --- |
| L1 常驻 | `mode:'always'` 规则全文（含项目规则） | `section`，order 100（不动） | 仅用户改规则时 |
| L2 索引 | `auto` 规则的目录：`[id] 标题 · 标签`，约 20~30 token/条 | 同一个 section 变量内 | 仅用户改规则时 |
| L3 场景全文 | 本轮命中的 `auto` 规则全文 | **`agent/pre-step` 注入 user 消息**（首选）或 `context()` | 每轮（sticky） |
| L4 兜底 | `ian_rules` 新增 `action:'lookup'`，模型按关键词/标签取全文 | 工具结果 | 模型决定 |

L3 首选 `agent/pre-step` 的理由：它是**唯一**能拿到 `messages` 的位置（`assemble` 在它之前跑完），而且 `dsh-tool-skill` 已经把这套做法跑通了——注入 `<system-reminder>` 形式的 user 消息（`dsh-tool-skill/lib/index.js:203-261`），并用 **sha256 目录摘要去重**，内容没变就不重复注入（`:219-226`、`:301-304`）。**去重是必须的**，否则每步都追加，历史会被自己撑爆。

为什么 L2 索引要常驻：**agent 得先知道自己有哪些规则可查**。索引成本极低（100 条约 2500 token，静态 → 缓存价 ≈ ¥0.0008/会话），而且它让 L3 漏命中不再致命。L2 必须**稳定**——不要放「本轮命中」标记或时间戳，否则 L1 和 L2 一起把前缀弄脏。

> 另可留意：宿主对**工具 schema** 有原生懒加载位（`deferLoading: true`，`dsh-llm/lib/types/types.d.ts:455-462`），DeepSeek 侧会发 `defer_loading`。但它只作用于工具定义，不能用来懒加载提示正文；不支持的适配器会直接抛错，**不建议**作为主路径。

### 4.5 可观测性（缺了这块不能上线）

1. **面板「效果预览」加场景模拟**：输入一句任务描述 → 列出命中规则、命中词、分数、预估 token。现有预览已能显示逐条 token 与「最占预算的 5 条」，接一个输入框即可。
2. **每轮命中回执**：L3 快照开头写一行，例如
   `本轮按场景命中 3 条（#12 提交前跑测试 / #31 依赖升级）；本项目另有 9 条规则可用 ian_rules lookup 取用。`
   让漏命中从静默变成可发现，同时天然提示了 L4。
3. **命中日志**（可选，默认关）：`$DSH_HOME/ian-rules.hits.jsonl`，用于回头调阈值。

### 4.6 风险与对策

| 风险 | 后果 | 对策 |
| --- | --- | --- |
| 漏命中 | agent 违规而用户无感 | L2 索引常驻 + L3 回执 + `sceneMatching:'off'` 一键退回 |
| 误命中 | 无关规则挤占预算 | 阈值 + top-K + 长度归一化 + sticky |
| 前缀被弄脏 | 本机路由下 **407×** 成本 | **硬性代码审查项**：动态内容只许进消息尾部；加源码级测试断言「不改规则的连续两步里，section 渲染结果逐字节相同」 |
| L3 每步重复注入 | 历史被撑爆 | sha256 去重（照 `dsh-tool-skill` 的做法） |
| 阈值难调 | 用户放弃 | 默认 `off`；先上 L1/L2/L4（不需要匹配算法），再上 L3 |

## 5. 落地计划

**编号说明**：P = Phase（阶段），数字越大越靠后，**不是**「两件事的两个选项」。

| 阶段 | 主题 | 可否独立发布 | 发布后线上行为 |
| --- | --- | --- | --- |
| **P0** | 修既有缺陷 | ✅ 可立刻单独发 | 更好，且不引入新概念 |
| **P1** | 数据模型与面板（为场景匹配铺路） | ✅ 可单独发 | **零变化**（刻意如此） |
| **P2** | 启用场景匹配 | ✅ 在 P1 之后 | 默认关（`sceneMatching:'off'`），用户手动开 |
| **P3** | 按需检索与调优 | ✅ | 增量 |

依赖关系：**P1 是 P2 的前置**（没有 `tags` / `mode` 字段，匹配器无从下手）；P0 与后面三步完全解耦，可以先做、先发。
P1 单独成阶段的理由：它动数据格式和面板，改完之后**渲染结果必须与旧版逐字节相同**——把「改造数据与 UI」和「匹配算法的风险」分开发布，才能让这条不变式被单独验证。

### P0 —— 独立于场景匹配，收益立竿见影

1. 修截断优先级：项目规则优先 + 列出被丢掉的规则 + 不在规则中间切。
2. 「保存并生效」加路由感知的代价说明与「下个会话生效」选项。
3. `ian_rules list` 默认摘要化，全文改为显式索取。
4. 祖先链合并（或至少告知父级规则集未生效）。
5. `variable` 回调改名 + 对未声明的 `agent` 字段加防御。

验收：新增测试若干；`npm run check` 全绿（当前基线 56/56 通过、身份自检通过）。

### P1 —— 数据模型与 UI（**不改注入行为**）

1. `DATA_VERSION = 2`，规则加 `mode` / `tags`，文档加 `sceneMatching`（缺省 `off`）。
2. `sanitizeDoc` 兼容 v1 + 「v1 文档渲染结果逐字节不变」黄金测试。
3. 面板：卡片加「常驻 / 按场景」开关与标签编辑；效果预览展示 L2 索引预览。

验收：现有测试全绿 + 黄金测试；线上行为零变化。

### P2 —— L3 场景全文注入

1. 匹配器（`lib/rules.js` 内纯函数，可单测）。
2. `agent/pre-step` 监听器注入 user 消息 + sha256 去重（首选）；或 `systemPrompt.context({name:'plugin:ian-rules-scene', order:130, text})`（次选，排在 `SUBAGENT_DELEGATION: 120` 之后）。
3. sticky 集合、每轮预算、命中回执。
4. 源码级测试：不改规则时 section 渲染逐字节稳定（守缓存）。

### P3 —— L4 工具与调优

1. `ian_rules` 加 `lookup`（按 query / tags 取全文，带条数与字符上限）。
2. 面板场景模拟器 + 命中日志。

## 6. 一句话回答「值得做吗」

值得，但要**换个理由、换个地方**：

- **换个理由**：收益是「规则容量不再被 12000 字符硬顶掉、注意力不被稀释、依从率上升」，不是「省 token」。有缓存的供应商上，规则只占会话成本不到 5%。
- **换个地方**：动态部分走 `agent/pre-step` 注入或 `systemPrompt.context()`，**绝不碰 `systemPrompt.section()`**。本机当前路由下放错一次，成本 ×407。
